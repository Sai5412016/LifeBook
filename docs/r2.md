## Grenzen dieser Stufe

- Beim Hochladen sind **Dateityp und genaue Größe** an die Signatur gebunden:
  `Content-Type` (der Typ aus der Datenbank, nicht der vom Handy behauptete)
  und `Content-Length` (die Byte-Zahl, die das Handy bei der Anfrage angibt,
  höchstens 50 MB). R2 nimmt deshalb nur genau diese Datei an.
- **Pflicht für die App (PR 2):** Der PUT muss exakt die Header aus der
  Antwort (`headers`) senden — `Content-Type` und `Content-Length` mit genau
  diesen Werten. Die Byte-Zahl in der Anfrage muss die echte Dateigröße sein
  (vor dem Signieren von der Datei lesen, nicht aus der Datenbank nehmen).
  Wird die Datei als „chunked" ohne Content-Length gesendet, oder weicht die
  Größe ab, antwortet R2 mit `403 SignatureDoesNotMatch`.
- `image/heif` wird abgelehnt (erlaubt sind jpg, png, heic, webp). Heute gibt
  es kein solches Foto.

## Hinweis für PR 2: `original_store` nie per Upsert mit NULL überschreiben

Der Trigger der Migration setzt bei **INSERT** ein NULL auf `'supabase'` und
behält bei **UPDATE** den alten Wert. Ein Upsert auf eine bestehende Zeile
(`INSERT … ON CONFLICT DO UPDATE`, `supabase-js .upsert()`, ein PUT, der
intern so umgesetzt wird) läuft aber durch den **INSERT-Zweig**: Aus NULL
wird dort `'supabase'`, und das `ON CONFLICT DO UPDATE` schreibt diesen Wert
dann über ein vorhandenes `'r2'`. Das Original wäre danach in der App „verloren“
(sie suchte es im falschen Speicher).

→ Bestehende `photos`-Zeilen dürfen **nie** per Upsert oder PUT mit
`original_store = NULL` hochgeladen werden. In PR 2 prüfen:
- `src/core/sync/connector.ts`: Stand 26.11.2026 setzt PUT als einfaches
  `insert()` um, ohne `ON CONFLICT`, und wertet 23505 als „schon vorhanden“.
  Damit wird eine vorhandene Zeile nicht überschrieben. Das muss so bleiben;
  ein Wechsel auf `.upsert()` ist hier zusätzlich zu Fallstrick 1 verboten.
- Alle lokalen `INSERT OR REPLACE`-Pfade auf `photos`: Ein `INSERT OR REPLACE`
  in der lokalen PowerSync-Datenbank erzeugt einen PUT für die ganze Zeile,
  mit allen lokal bekannten Spalten — ist `original_store` lokal NULL, geht
  NULL mit. Stand 26.11.2026 gibt es keinen solchen Pfad auf `photos` (nur
  auf der rein lokalen Tabelle `photo_backups`).
- Wer in PR 2 `original_store = 'r2'` setzt, tut das per **UPDATE** (PATCH)
  auf genau diese Spalte, nie über ein Neuanlegen der Zeile.

## 4. PR 2 — die App benutzt R2 (Branch `feature/r2-originale`)

**Schalter:** `src/core/storage/originals-config.ts` → `ORIGINALS_TO_R2`
(Standard `true`). Auf `false` setzen und ein Funkupdate ausliefern → neue
Originale gehen wieder zu Supabase. Gelesen wird IMMER nach der Spalte
`original_store` der Zeile, ein Zurückschalten macht also kein R2-Original
unerreichbar.

**Ablauf beim Hochladen eines NEUEN Originals** (nur auf dem Handy, das das
Foto importiert hat, wie bisher erst im WLAN, nach Vorschau und Medium):

1. Dateigröße direkt von der Datei lesen
   (`storage.ts#localFileSize` über `original-store.ts#uploadOriginal`).
2. `media-sign` `put` mit `photo_id`, `content_type`, `bytes`
   (`core/storage/media-sign.ts#requestMediaSign`).
3. Prüfen, dass die Antwort genau diese Länge und diesen Typ signiert hat
   (`media-sign-protocol.ts#assertPutHeadersMatch`).
4. PUT mit `File.upload(…, { httpMethod: 'PUT', uploadType: BINARY_CONTENT,
   headers })` — exakt die Header aus der Antwort
   (`media-sign.ts#putFileToR2`). Sendet eine echte `Content-Length`, kein
   „chunked" — Nachweis im Kommentar dort (expo-file-system 57.0.2:
   `asRequestBody` → `contentLength() = length()` der Datei; OkHttp setzt
   daraus `Content-Length`).
5. `media-sign` `get`, dann ein Byte per `Range: bytes=0-0` von R2 holen;
   R2 nennt die Gesamtgröße in `Content-Range`
   (`media-sign.ts#probeR2ObjectSize`). Kein HEAD: Eine signierte GET-Adresse
   gilt nur für GET.
6. Nur wenn gespeicherte Größe == lokale Größe: EIN lokales UPDATE setzt
   `original_uploaded_at` UND `original_store = 'r2'`
   (`repository.ts#markOriginalUploaded(…, 'r2')`), danach darf die Kopie in
   `photos-pending` weg (unverändert: `isSafeToDeleteStagedCopy`).
7. Jeder Fehler (403 SignatureDoesNotMatch, 5xx, Netz, Größe falsch) wirft:
   bestehender Retry mit Pausen, Zeile unverändert, Kopie bleibt.

**Lesen eines Originals** („Original senden", „Alle Fotos sichern", Nachrechnen
eines fehlenden Mediums): lokale Kopie, sonst bei `'r2'` über `media-sign get`,
sonst Supabase wie bisher (`storage.ts#resolveOriginalForSharing`).

**Teilen:** „Teilen" schickt das Medium (1600 px). Es wird vor dem Teilen auf
EXIF/XMP/IPTC geprüft und, falls doch etwas drinsteht, bereinigt
(`jpeg-metadata.ts`, `storage.ts#resolveMediumForSharing`). „Original
senden" ist die zweite, ausdrückliche Option mit dem Hinweis „enthält ggf. den
Aufnahmeort".

**Vollbild/Startseite:** signiert nur noch das Medium; das Original nur bei
alten Fotos ohne Medium, und nur aus Supabase
(`original-store.ts#fullscreenKeysToSign`).

**Endgültig löschen:** bei `'r2'` zusätzlich `media-sign delete`, VOR dem
Löschen der Zeile. Scheitert das, wird die Zeile trotzdem gelöscht und der
Fehler auf dem Handy gemerkt (`r2-delete-queue.ts`), Neuversuch beim
nächsten App-Start, Anzahl in Einstellungen → Papierkorb-Zeile. **Grenze:**
Ist die Zeile auf dem Server schon weg, kann `media-sign` nicht mehr
signieren (es nimmt den Schlüssel bewusst nie vom Handy) — solche Objekte
bleiben als Waisen in R2, mit Schlüssel auf dem Handy vermerkt. Aufräumen
serverseitig in PR 3.
