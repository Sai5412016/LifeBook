(das kommt mit PR 2). Dieser Teil schafft nur die Grundlage:

- `supabase/functions/media-sign/` — stellt nach Prüfung von Anmeldung und
  Haushaltsrolle eine kurzlebige, signierte Adresse für **ein** Original in R2

  dem angegebenen Typ und der angegebenen Größe).
- `supabase/migrations/20261126114058_photos_original_store.sql` — neue Spalte
  `photos.original_store` (`'supabase'` oder `'r2'`).

**Wer was darf** (aus den Datenbankregeln übernommen, nicht neu erfunden):
Lesen jedes Haushaltsmitglied, Hochladen und Löschen nur `owner` und
`caregiver` — dieselbe Regel wie `public.auth_writable_household_ids()`, die
heute schon Tabelle und Speicher `photos` schützt. `viewer` darf nur lesen.

## 1. Die vier Secrets (Namen und Fundstelle — Werte nie weitergeben)

Eintragen in: supabase.com/dashboard → Projekt **lifebook** → links
**Edge Functions** → **Secrets** → **Add new secret** (Name exakt wie unten).

| Name | Wert | Fundstelle |
|---|---|---|
| `R2_ENDPOINT` | `https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com` | Cloudflare → **R2 Object Storage** → **Overview** → Kasten **Account Details** → Account ID. Mit `.eu.`, ohne Bucket-Namen, ohne Schrägstrich am Ende. Derselbe Wert wie das GitHub-Secret `R2_ENDPOINT` vom Backup. |
| `R2_ACCESS_KEY_ID` | Access Key ID | Das vorhandene R2-Token mit „Object Read & Write" für `lifebook-originals` und `lifebook-backups` (im Passwortmanager). |
| `R2_SECRET_ACCESS_KEY` | Secret Access Key | Dasselbe Token. Cloudflare zeigt ihn nur beim Anlegen. Verloren? R2 → **Manage API tokens** → neues Token mit „Object Read & Write", nur diese beiden Buckets, dann **auch** die GitHub-Secrets des Backups auf das neue Token umstellen. |
| `R2_BUCKET_ORIGINALS` | `lifebook-originals` | genau so eintragen |

`SUPABASE_URL` und `SUPABASE_SERVICE_ROLE_KEY` stellt Supabase jeder Function
selbst bereit — nicht eintragen.

## 3. Testen

### Ohne Netz: die Logik (läuft bei jedem `npx vitest run`)

```
npx vitest run supabase/functions/media-sign
```

Prüft die Signatur gegen die offiziellen AWS-Beispielwerte, die Pfadbildung,
die Rollen, die Ablaufzeiten und alle Fehlercodes.

### Lokal mit Supabase-CLI (optional, braucht Docker)

1. Datei `supabase/functions/.env.local` anlegen (steht nicht im Repo, nie
   einchecken) mit den vier Secrets aus Abschnitt 1.
2. Starten:
   ```
   npx supabase functions serve media-sign --env-file supabase/functions/.env.local
   ```
3. In der App angemeldet ein Zugangstoken besorgen (oder aus der
   Supabase-Konsole eines Testnutzers) und aufrufen:
   ```
   curl -X POST http://localhost:54321/functions/v1/media-sign ^
     -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" ^
     -d "{\"photo_id\":\"<FOTO-ID>\",\"op\":\"get\"}"
   ```
   Erwartet: `200` mit `url`, `method`, `key`, `expires_at`. Ohne Token
   `401`, mit fremder Foto-ID `404`, als `viewer` mit `"op":"put"` `403`.

### Nach dem Deploy: Probe gegen R2

- `op: "get"` für ein Foto, dessen Original noch NICHT in R2 liegt, liefert
  eine gültige Adresse — deren Abruf antwortet von R2 mit `404 NoSuchKey`.
  Das ist richtig und beweist, dass Signatur und Endpoint stimmen (ein
  Signaturfehler hieße `403 SignatureDoesNotMatch`).
- Hochladen probiert erst PR 2 aus der App.

## Grenzen dieser Stufe

- Beim Hochladen sind **Dateityp und genaue Größe** an die Signatur gebunden:
  `Content-Type` (der Typ aus der Datenbank, nicht der vom Handy behauptete)
  und `Content-Length` (die Byte-Zahl, die das Handy bei der Anfrage angibt,
  höchstens 50 MB). R2 nimmt deshalb nur genau diese Datei an.
- **Pflicht für die App (PR 2):** Der PUT muss exakt die Header aus der
  Antwort (`headers`) senden — `Content-Type` und `Content-Length` mit genau
  diesen Werten. Die Byte-Zahl in der Anfrage muss die echte Dateigröße sein
  (vor dem Signieren von der Datei lesen, nicht aus der Datenbank nehmen).
  Wird die Datei als „chunked" ohne Content-Length gesendet, oder weicht die
  Größe ab, antwortet R2 mit `403 SignatureDoesNotMatch`.
- `image/heif` wird abgelehnt (erlaubt sind jpg, png, heic, webp). Heute gibt
  es kein solches Foto.

## Hinweis für PR 2: `original_store` nie per Upsert mit NULL überschreiben

Der Trigger der Migration setzt bei **INSERT** ein NULL auf `'supabase'` und
behält bei **UPDATE** den alten Wert. Ein Upsert auf eine bestehende Zeile
(`INSERT … ON CONFLICT DO UPDATE`, `supabase-js .upsert()`, ein PUT, der
intern so umgesetzt wird) läuft aber durch den **INSERT-Zweig**: Aus NULL
wird dort `'supabase'`, und das `ON CONFLICT DO UPDATE` schreibt diesen Wert
dann über ein vorhandenes `'r2'`. Das Original wäre danach in der App „verloren“
(sie suchte es im falschen Speicher).

→ Bestehende `photos`-Zeilen dürfen **nie** per Upsert oder PUT mit
`original_store = NULL` hochgeladen werden. In PR 2 prüfen:
- `src/core/sync/connector.ts`: Stand 26.11.2026 setzt PUT als einfaches
  `insert()` um, ohne `ON CONFLICT`, und wertet 23505 als „schon vorhanden“.
  Damit wird eine vorhandene Zeile nicht überschrieben. Das muss so bleiben;
  ein Wechsel auf `.upsert()` ist hier zusätzlich zu Fallstrick 1 verboten.
- Alle lokalen `INSERT OR REPLACE`-Pfade auf `photos`: Ein `INSERT OR REPLACE`
  in der lokalen PowerSync-Datenbank erzeugt einen PUT für die ganze Zeile,
  mit allen lokal bekannten Spalten — ist `original_store` lokal NULL, geht
  NULL mit. Stand 26.11.2026 gibt es keinen solchen Pfad auf `photos` (nur
  auf der rein lokalen Tabelle `photo_backups`).
- Wer in PR 2 `original_store = 'r2'` setzt, tut das per **UPDATE** (PATCH)
  auf genau diese Spalte, nie über ein Neuanlegen der Zeile.
